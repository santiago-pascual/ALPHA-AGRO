# Phase 6A — NASA data availability and operational forecast feasibility

**Research checked:** 2026-11-15 (UTC)
**Status:** feasibility foundation only. No NASA archive was downloaded, no operational forecast was issued, and no source's Pampas delivery latency was empirically measured in this work.

## Executive finding

Prospective 1–3 month soil-water forecasting is **technically feasible to investigate**, but is not yet demonstrated or ready for a user-facing forecast. A low-latency weather/soil-moisture feature stack exists in provider documentation: SMAP surface/root-zone products, IMERG near-real-time precipitation, and NASA POWER meteorology. NASA's GEOS-S2S-3 is a potential source of seasonal ensemble drivers. Important blockers remain: GLDAS Noah v2.1 target latency and revisions; absent historical, issue-time input vintages; no measured Pampas first-access logs; uncertain access to a repeatable GEOS-S2S-3 Pampas feed; and the mismatch between SMAP retrieval/model states and the GLDAS Noah 0–100 cm storage target.

The machine-readable registry is [availability_registry_v1.json](../config/availability_registry_v1.json). It records expected source properties separately from per-granule availability evidence. Its evidence-record list is empty, by design: no actual first-successful asset requests were recorded in this task. Running the checker therefore returns `no_verified_inputs`; unknown and expected release states cannot become verified by latency arithmetic.

## Evidence labels

- **Documented fact** means the provider's current product or help documentation describes that product property or a typical latency. It does not mean this project observed a file at that time.
- **Verified available** means a time-stamped successful request to the actual granule/asset was captured and preserved. A catalog listing, expected lag, file observation period, `ProductionDateTime`, or later successful download does not by itself prove the file was available at an earlier issue time.
- **Assumption/open question** marks a proposed use or any fact not established by the provider pages reviewed here.

### Access, timestamps and restrictions

GES DISC does not have one universal release clock for all products. Its tools include HTTPS, OPeNDAP/GDS, spatial/temporal/variable subsetting and Giovanni. Giovanni full access/data holdings require Earthdata Login and authorization of the GES DISC archive application; guest mode is limited. NASA Earthdata supports authenticated cURL/Wget and application authorization. POWER's public API is a simpler public service and does not document an Earthdata credential/API-key requirement. [GES DISC access overview](https://ldas.gsfc.nasa.gov/gldas/gldas), [Giovanni user guide](https://giovanni.gsfc.nasa.gov/giovanni/doc/UsersManualworkingdocument.docx.html), [Earthdata Login access guide](https://urs.earthdata.nasa.gov/documentation/for_users/data_access/curl_and_wget).

CMR UMM-G documents `ProductionDateTime` and `ProviderDates`: `Create` is the file creation/production date, `Insert` is the provider database insert date, and `Update` is a metadata/file update date. They are valuable provenance and monitoring fields, but `Insert` is not defined as the first moment a file was accessible to a public user. CMR metadata does not reconstruct a complete historical HTTP-availability log. A `Last-Modified` header is also not a first-publication timestamp. [CMR Provider Dates definition](https://wiki.earthdata.nasa.gov/spaces/CMR/pages/135834714/Provider%2BDates), [CMR metadata best practices](https://wiki.earthdata.nasa.gov/spaces/CMR/pages/148735360/CMR%2BMetadata%2BBest%2BPractices%2BLanding%2BPage), [CMR search API](https://cmr.earthdata.nasa.gov/search/site/docs/search/api.html).

NASA-led scientific data are generally CC0 unless the individual collection/file carries a different restriction. Check each product's current use constraints, cite the dataset DOI and provider, preserve attributions, and check any re-hosting/redistribution rules. Earthdata Login is free; access is still subject to account/application authorization and provider controls. [NASA Science Data License guidance](https://science.data.nasa.gov/about/license).

**Publication-time answer:** machine metadata can expose production and provider-catalog event times when the provider populates them. I did not find a universal GES DISC per-granule “first public HTTP success” timestamp or complete immutable schedule. The most defensible operational record is the project’s own timestamped successful asset probe and archived asset checksum/version. A successful download today cannot establish that the same bytes were available at a historical forecast issue date.

## Availability registry and as-of checker

The registry at `config/availability_registry_v1.json` records product identifiers, versions, variables/units, temporal and spatial support, historical coverage, documented expected latency, timestamp evidence, URLs/authentication, use notes, Pampas relevance, and quality flags. Current source-level status is deliberately `expected_available_not_verified` or `unknown`; `availability_records` is empty because no asset requests were performed. The four per-record states are:

| Status | Meaning | Eligible at an issue time? |
|---|---|---|
| `verified_available` | First successful actual-asset HTTP request was recorded with UTC timestamp, 2xx response and evidence URL. | Yes, only when that timestamp is at or before issue time. |
| `expected_available_not_verified` | An expected timestamp/latency is documented, but asset access has not been verified. | Never. |
| `unavailable` | A dated provider observation/evidence says the requested asset was unavailable. | Never. |
| `unknown` | No qualifying per-record evidence. | Never. |

The validator rejects a `verified_available` row without successful request evidence. A CMR provider insert date alone is not acceptable. Registry rows also retain observation interval, publication timestamp/basis, evidence, and data-quality flags. The checker is offline and does not fetch NASA data or issue forecasts.

```powershell
& .\.venv\Scripts\python.exe -m gldas.availability validate
& .\.venv\Scripts\python.exe -m gldas.availability check --issue-time 2026-11-15T12:00:00Z
& .\.venv\Scripts\python.exe -m gldas.availability check --issue-time 2026-11-15T12:00:00Z --registry path\to\local_registry.json
```

The second command currently returns `no_verified_inputs`. To populate records, a monitor must record the granule ID, source/variable/units, observation bounds, UTC timestamp of the first successful asset request, request URL, HTTP status, immutable product version, file hash if acquired, and QA/missingness flags. Keep NASA credentials out of registry files and logs.

## Candidate prospective architecture

1. **Target and long historical baseline:** retain GLDAS Noah v2.1 monthly 0–100 cm aggregate as the existing model-defined target. Preserve final and Early Product streams as distinct vintages. Do not claim the target was known on its observation date.
2. **Low-latency weather:** aggregate IMERG V07 Late precipitation to consistent daily/monthly intervals and ingest NASA POWER daily temperature in explicit UTC (or one fixed documented local-time standard). Store source field, source version, quality masks, grid mapping, and response timestamps.
3. **Recent soil-moisture features:** test SMAP L3 surface retrievals and L4 `sm_rootzone` as separate features from 2015 onward. Do not substitute them for GLDAS Noah storage. L4's model assimilation and IMERG forcing make it a model-informed proxy with shared inputs.
4. **Seasonal predictor:** request GEOS-S2S-3's Pampas precipitation/temperature subset, member spread and retrospective forecasts. Keep this feature disabled until exact product fields, access cadence, reforecast availability, and first-download evidence are established. If unavailable, an observations-only model may be researched, but its skill must be evaluated as that different system.
5. **Availability-aware feature store:** store each value with observation interval, `available_at` (project first-successful-access time), source product/version, revision/hash, mask/quality, and transformation. At issue time, include only rows whose recorded `available_at <= issue_time`; freeze each issued feature vector and model version.
6. **Validation:** replay archived issue-time snapshots (not the current revised archive) with expanding chronological validation plus a final untouched holdout. Use a matched evaluation period after SMAP begins for satellite-informed variants; separately report the longer GLDAS-only record. Compare with persistence/climatology and calibration baselines; quantify score uncertainty; validate target against in-situ soil moisture where quality-controlled Pampas observations are available.

### Storage and surface-moisture compatibility

The dashboard target is GLDAS Noah water stored through 0–100 cm, a layered model storage sum in kg m⁻² (equivalent numerically to mm water). SMAP L3 is a radiometer-derived **near-surface** volumetric moisture retrieval in m³/m³, posted on a 9 km grid. It has different sensing depth, units, overpass sampling, quality masks, effective footprint and error structure. It cannot be added or compared directly as if it were the same variable. SMAP L4 provides `sm_rootzone` in volumetric units, but it is a Catchment-model state informed by SMAP brightness temperatures and other model forcing, and its definition/grid/version must be checked. A conversion to water-column units is only defensible after confirming the exact integration depth and semantics; resample both sources with explicit area/coverage weights and validate against independent profile measurements. L4 also uses IMERG V07 precipitation outside North America/high latitudes, so SMAP L4 plus IMERG does not constitute independent precipitation confirmation.

## Feasibility, risks and open questions

**Technical feasibility:** A low-cost ingestion and monitoring pipeline is feasible using free NASA services. The 1–3-month predictor problem is plausible if GEOS-S2S-3 ensemble inputs can be accessed consistently and their retrospective issue-date vintages can be matched. Near-real-time observed inputs (IMERG/SMAP/POWER) mainly improve the initial state; they do not themselves provide future-month meteorology. A model with only these observations must establish predictive skill from persistence, seasonality and recent anomalies; the existence of an API does not demonstrate skill.

**Documented latency is not empirical availability.** Published GLDAS and NSIDC/IMERG/POWER latency values are product/service expectations or processing generation latency. Asset ingest, data-center indexing, authentication, outage, and product revision can shift actual first access. The checker is deliberately fail-closed. This checkout has no project monitoring evidence for any NASA record.

**Main open questions:**

- Which GLDAS timing applies to the active Pampas product stream? The current general FAQ (~1 month) and product-specific GLDAS 2.1 main README (~3–4 months, EP ~1.5 months) differ. How often is EP emitted now, and how are its granules removed/replaced?
- Do CMR `ProviderDates.Insert` and provider download logs align with the first successful GES DISC HTTPS/OPeNDAP response? Does that differ by source, authentication state, and outage?
- Can NASA provide a stable GEOS-S2S-3 0–3-month Pampas subset, with precipitation/temperature fields, ensemble identifiers, a reproducible cadence, and a comparable multi-year reforecast archive? What is the authorization and redistribution policy?
- What root-zone depth does the selected SMAP L4 V8 field represent in the actual file's guide/metadata, and can it be validated against soil-profile observations in the region?
- Which local Argentine station/profile data have reliable quality flags, coverage, coordinates and use permissions for independent validation?
- How will output freshness be stated when the GLDAS Noah target itself arrives weeks/months after its observation period?

Do not call a future metric an operational forecast skill score until a frozen issue-time dataset/vintage replay shows an untouched prospective-like holdout and the live pipeline's availability assumptions are audited.

## Recommended minimal viable operational data stack

1. GLDAS Noah v2.1 monthly main for consistent historical target construction; optionally test the separate Early stream as an explicitly different, short-latency feature.
2. IMERG V07 Late (0.1°, half-hourly, daily aggregates) for recent precipitation, using the latest accessible vintage with logged version/availability time.
3. NASA POWER daily `T2M`, `T2M_MAX`, `T2M_MIN` in UTC for recent temperature; document the coarser MERRA-2/GEOS-IT source transition.
4. SMAP L4 `sm_rootzone` as a separate 2015-onward auxiliary feature only after depth/units/quality and independent evaluation are established; add SMAP L3 only as a surface retrieval comparison/feature, not a substitute target.
5. GEOS-S2S-3 seasonal meteorology only after GMAO confirms repeatable Pampas access and the hindcast contains historical forecast issue/vintage files. Keep operational forecasts withheld until this gate passes.

This stack is a recommendation for an availability and hindcast experiment; it is not a claim of validated forecast accuracy.

## Concrete publication-latency experiment

Run a **120-day, no-bulk-download monitor** on the original data-holding PC, or another approved machine with Earthdata access:

1. Resolve and pin CMR concept IDs/versions for GLDAS monthly main and EP, GLDAS 3-hourly, IMERG V07 Early/Late, SMAP L3 V6, and SMAP L4 V8. Pin selected POWER parameters and a GEOS-S2S-3 Pampas request if GMAO approves access.
2. Poll public CMR metadata more frequently than product assets: every 3 hours for IMERG and daily for SMAP/GLDAS/POWER status. When a new target granule appears, request a small HTTP byte range or the smallest valid spatial/temporal subset from the asset service. Observe GLDAS monthly assets daily across at least four month boundaries. Keep request volume small and obey provider rate limits.
3. Save immutable UTC records of each poll, HTTP status, redirects, response headers, CMR concept ID, `ProductionDateTime`, `ProviderDates`, exact version/run, URL, and asset SHA-256 where a complete small subset/file is retrieved. Never save credentials. Keep first-success time separate from CMR insert/production times and distinguish subsequent replacement/reprocessing.
4. For every granule, compute `first_success_utc - observation_end_utc`, stratified by product/version and by first-vs-final/updated vintage. Report sample count, median, p90/p95, max, failures, missing/quality coverage and revision frequency; publish raw monitor log hashes and the cutoff rule. With a 120-day window the GLDAS main product yields only a few monthly cycles, so extend monitoring if that sample is too small to describe a latency distribution.
5. Test the as-of checker against the immutable log: at each scheduled issue timestamp, only records whose first successful access is earlier/equal are returned. Then attempt a historical walk-forward replay using the saved vintages. If old issue-time vintages cannot be recovered, do not reconstruct them from today's final archive; mark those predictor records unknown and withhold operational skill claims.

**Success condition:** the test yields reproducible per-source first-success distributions and reconstructable feature snapshots for each validation issue date. A source that only has a documented lag or current catalog presence remains `expected_available_not_verified` or `unknown` in the registry.

## Reproduction and current implementation scope

- Validate the static source registry: `python -m gldas.availability validate`
- Query verified inputs as-of an issue time: `python -m gldas.availability check --issue-time 2026-11-15T12:00:00Z`
- Run only synthetic offline unit tests: `python -m pytest tests/test_availability.py -q`

The registry is metadata-only; `availability_records` is empty. Test timestamps/URLs live only in a fixture labeled synthetic. This phase adds no network acquisition, full-archive downloads, paid integrations, operational forecast execution, frontend changes, or predictive evaluation results.
